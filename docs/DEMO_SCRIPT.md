# Demo and ten minute presentation script

## Startup

Windows PowerShell from the repository root:

```powershell
.\.venv\Scripts\python.exe -m src.model.train
.\.venv\Scripts\python.exe -m streamlit run src/ui/app.py
```

With an activated environment, use `python -m src.model.train` then `python -m streamlit run src/ui/app.py`. Linux uses `.venv/bin/python`.

## Reliable demonstration

1. State that the network and history are synthetic and the weather is a hypothetical scenario.
2. Select origin **S04 Vidhansabha Marg**, destination **S14 Polytechnic Crossing**.
3. Select **18:00**, **Thursday**, **Storm**, event **off**, preference **2.0**.
4. Expect baseline **S04 → S01 → S12 → S14**, **22 minutes**, **1 transfer**, mean **0.405926**, maximum **0.525010**.
5. Expect recommendation **S04 → S18 → S15 → S14**, **25 minutes**, **1 transfer**, mean **0.322975**, maximum **0.334890**.
6. Signed reduction is **20.435%**, additional duration **+3.0 minutes**. Both encounter **zero** stations with congestion >=0.70. Compare the table and hover the network points.
7. Change preference to zero: both methods have the same itinerary and 0% reduction. Choose the same origin and destination: duration is zero and exposure remains that station's prediction.

This example is selected from the saved full-grid CSV. It is not the aggregate improvement rate. The benchmark also reports unchanged and worsened cases.

## Timed narration

The timing allocates about ten minutes, including the live comparison on slide five. Rehearse at a natural pace; the notes below support technical explanation rather than reading every word.

### Slide 1 Problem and motivation

0:00-1:40. Our project is Smart Public Transport System: Crowd-Aware Route Optimization, for Software Engineering at IIIT Lucknow. We address one problem: a conventional route can be quick while passing through crowded stations, because its travel-time objective does not account for congestion. A commuter may accept some additional travel time to avoid that exposure. Our objective is therefore to compare predicted station exposure with travel duration rather than hide the trade-off.

We chose this problem because it gives a concrete and testable connection between requirements, machine learning and graph algorithms. The output is a route recommendation, but the core problem remains crowd exposure. We do not add payment, booking or account features.

The whole study is a simulation. The network has illustrative lines inspired by Lucknow, and every historical observation is generated by a reproducible program. We have not measured real passengers or established a citywide benefit. This disclosure is visible in the dashboard and in the documents. Keeping the scope small lets us explain exactly what each prediction and route cost means.

### Slide 2 Approach and Software Engineering

1:40-3:30. The architecture separates five responsibilities. Data loading checks CSV schemas, value ranges and timestamps. The model transforms scenario inputs into numeric station congestion predictions. The graph builder preserves parallel transit lines. The router takes the graph and a prediction map, runs the conventional and crowd-aware searches, and returns plain result dictionaries. Streamlit displays these results.

The same station files and model interface serve the application and benchmark. Prediction runs once per scenario, rather than once for every search relaxation. That keeps model concerns outside the search algorithm and makes both parts easier to test.

Software Engineering connects the implementation to the problem. We wrote acceptance criteria and mapped eight functional requirements to tests. We audited two competing implementations, retained the stronger continuous-regression pipeline, and preserved the alternative source in a legacy archive. We corrected defects incrementally and added regression cases after reproducing them. This is an audit-led incremental process, not a claim that the whole original project was developed using TDD. CI executes the supported training, testing and benchmark commands on Windows and Ubuntu.

### Slide 3 Why this technical approach

3:30-5:30. Each segment contributes its base minutes. A change from the previous line adds four minutes. The crowd term multiplies the destination station discomfort by 2.5 and the selected preference. Zero preference gives exactly the conventional objective with the same transfer assumption. The discomfort curve is continuous and nondecreasing, with thresholds at 0.35 and 0.70. It is an assumption about discomfort, not measured boarding delay.

We use Dijkstra because every increment is non-negative. The state must contain both station and previous line: arriving on a different line can change the next transfer cost. A unique heap counter handles equal costs safely. An adjacency-based multigraph retains parallel services without a dense matrix. BFS would optimize edge count, while A* needs an admissible heuristic we have not validated. Reinforcement learning adds complexity without a requirement on this static graph.

The model comparison used validation data, not the final test. Random Forest had the lowest validation RMSE. Its features are cyclic time and weekday, derived peak and weekend, station, weather and event. Generated passenger counts, delay and the congestion target are excluded. Path lists are copied during search, so our documented complexity includes that overhead rather than quoting only a textbook bound.

### Slide 4 Software testing and stopping criteria

5:30-7:30. The recorded suite has 74 passing cases. Statement coverage is 93.62% and branch coverage is 95.00% for ingestion, prediction and routing, including the training CLI module. The routing and cost modules achieve 100% on both measures. These percentages do not cover the UI, document scripts, benchmark script or archived implementation, so we do not describe them as whole-repository coverage.

We select cases by equivalence partitions and boundaries: valid versus unknown stations, connected versus disconnected graphs, hour endpoints, crowd thresholds, zero preference and invalid values. Transfer decision cases distinguish initial boarding, same line and changed line. Error guessing adds NaN, infinity, broken artifacts, missing files and duplicate data. Regression tests lock the important defects we fixed.

For independent validation, we assemble a separate NetworkX station-and-line state graph on controlled random networks and compare minimum costs. AppTest executes actual Streamlit controls, including zero preference, an identity trip and weekend, weather and event changes. We stop at explicit gates: all required cases pass, coverage exceeds the threshold, every requirement is mapped, and setup, benchmark and app workflows succeed. We did not run fault seeding or a Musa reliability experiment, so no statistical reliability claim follows.

### Slide 5 Outcomes and innovation

7:30-10:00, including a one-minute live demonstration. We evaluated all 380 ordered distinct station pairs across seven scenario regimes and four preferences, giving 10,640 comparisons. 4.02% improved average exposure, 95.67% kept the same itinerary, and 0.31% worsened exposure. Mean signed reduction is only 0.333%, so the aggregate benefit is modest. We keep the adverse rows because the optimizer minimizes accumulated nonlinear discomfort, while the displayed metric is an arithmetic mean.

For a reliable demonstration, choose S04 to S14, Thursday at 18:00, Storm, no event, preference two. The baseline goes through S01 and S12, takes 22 minutes, and has mean predicted congestion 0.405926. The recommendation goes through S18 and S15, takes 25 minutes, and has mean 0.322975. That is a 20.435% reduction with three extra minutes. Both have one transfer and neither reaches our high-congestion threshold. Show the route and return preference to zero to demonstrate identical objectives.

Our contribution is the reproducible integration and transparent comparison, not a new shortest-path theorem. There is no LLM or ChatGPT call: a fitted regressor predicts numbers and a deterministic algorithm selects routes. Synthetic data, fixed times and departure snapshots limit deployment claims. Real use would require observed data, calibrated preferences and fresh external validation.
